<locked_conventions>
These answer research open questions 3 and 4 and assumptions A1-A3; they are locked by this plan, documented in
docs/hardware/bus.md here and in docs/hardware/maria.md by plan 03-03:
- Beam position: `m->maria.origin` is the tick of line 0, t 0 of the current frame; line = (ticks - origin) / 454, t = (ticks - origin) % 454, and the origin advances by 119,402 at each VBLANK start crossing. The frame boundary is line 258, t 42.
- Fast-boot frame 1: the hand-off is line 240, t 24; frame 1 is the 8,190 ticks to the first VBLANK start; frame rows not scanned since load (rows 0-223) are written $00; the audio count of any frame is (audio_rem + elapsed_ticks * 88) / 13,125 where elapsed is the distance between the two VBLANK-start deadlines, so a full frame still gives 800 or 801 and frame 1 gives 54.
- Overshoot: the loop stops at the first instruction boundary at or after the deadline; deadlines are absolute ticks, so overshoot carries into the next frame and frames never drift.
- `cpu_phase` 0: the hand-off tick t 24 is a multiple of 4 (A7800-SYSTEM C10), fitted, RTL check in v4.0.
- HALT from MARIA: the request at t 28 passes `until_tick = MUHTARI__HALT_UNTIL_MARIA` (UINT64_MAX); when the window reaches c2 the bus calls `muhtari__maria_burst(m, fall_tick)`, which runs the burst with T0 = fall + 6 and returns HALTRST as the hold's end. Explicit `until` values (the existing bus tests) behave as before.
- Rows until plan 03-03: with content loaded, every row of `io->video` that MARIA has not rendered is written $00, so frames are deterministic before span rendering lands (a functionality gap that plan 03-03 fills without changing the loop).
</locked_conventions>
