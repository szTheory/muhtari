## Wiring summary

Phase 28 provides the measured, source-qualified CI/release baseline and corrected register counts. Phase 29 consumes Phase 28's source-qualified maintenance baseline in its plan prerequisites, test strategy, acceptance record, and decision to preserve coverage and use a scheduling-only CTest adjustment. The phase dependency is explicit in `29-01-SUMMARY.md` and the evidence is retained in `28-TUNEUP.md`.

Phase 29 is a runner-only feature. It does not export a new library API or alter libretro wiring. The CLI path flow is connected through `runner/main.c`: Windows `wmain` receives wide arguments, `WideCharToMultiByte` converts them strictly to UTF-8, `runner_path_arguments_supported` checks each path option, and the path helpers convert back to UTF-16 for `_wopen`, `CreateFileW`, `MoveFileExW`, and related file operations. The path identity preflight compares all output/input and output/output pairs before emulation, including the derived battery output.

The acceptance driver starts the actual `muhtari-run` executable with `CreateProcessW`, then independently checks path spellings, resulting bytes, identity, failures, and cleanup. The Windows branch of `tests/runner/trace.cmake` registers it as `runner.trace.paths`; the existing CI matrix runs the `ci-msvc` workflow on Windows x64 and ARM64, and the workflow rejects missing drive, UNC, or SMB lifecycle measurements. `docs/runner.md` describes the same bounded path contract.

## CI-efficiency follow-up: release-please pre-merge gate

The new `ci.yml` exception is connected through a narrow trust chain. The workflow sets `RELEASE_METADATA_PR=true` only when the PR head repository equals the current repository, the head branch is exactly `release-please--branches--main`, and the base is exactly `main`. The API listing passes both the new and prior filename for renames through `classify-pr-paths.jq`; either name containing a line feed emits only the failure sentinel before the line-delimited transport. The classifier also receives GitHub's changed-file count. It returns `heavy=false` for this exception only when the count is 3 and the three unique paths are exactly `.release-please-manifest.json`, `CHANGELOG.md`, and `version.txt`; missing, extra, duplicated, renamed, oversized, newline-bearing, or unlisted paths leave heavy CI enabled. A fork or different branch/base cannot request the exception.

`hygiene` remains unconditional, `title` still runs on every pull request, and the `CI required` job still runs with `if: always()` over the complete job result map. Its allow-list permits heavy jobs to be skipped only when `changes` classified the PR as light; it does not allow hygiene, title, or the required roll-up to be skipped. Thus the release-please PR still needs those three required checks to pass.

The release workflow retains the publication gates: `release-target` provides the immutable release SHA; reusable `release-ci` and `release-equality` both receive that exact SHA; and `publish` requires a created release plus success from both jobs before downloading artifacts, attesting, or uploading. A reusable CI call has no pull-request number, so its classifier sets `heavy=true` and runs the full matrix. The pre-merge shortcut therefore does not replace exact-source CI or equality.

The local `cmake --workflow --preset hygiene` run passed 31/31 tests in 32.46 seconds. The expanded `ci.classify` cases cover the exact metadata set and order, missing/extra/duplicate paths, wrong count, newline spoof attempts in current and prior filenames, and an otherwise exact set with an untrusted branch flag. A simulated partial API listing emits a failure sentinel and remains heavy. `ci.classify.workflow_guard.self_test` mutates the workflow guard and requires the check to fail. Standard code review first found the newline transport issue; the corrected filter and tests now leave no findings. This proves local classifier and guard behavior, not a hosted release-PR result.
