# v3.0 milestone audit — Playstead-ready play and states

## Decision

The original v3.0 definition of done is not met. Close the milestone only as an
explicit override with deferred requirements. Keep all phase evidence and stops
intact; do not mark host behavior or the Windows improvement as passed. Phase 13
is the delivered and verified portion of v3.0.

The audit uses the repository's strict three-source rule. A requirement counts as
satisfied only when its phase verification passed, a phase summary lists it in
`requirements-completed`, and the milestone traceability table marks it Complete.
Phase 13 now has that summary mapping for its seven passed requirements. The
Phase 12 and Phase 14 requirements remain unsatisfied for milestone closeout
because those phase verifications are `gaps_found` and the requirements remain
Pending, even where Phase 12's verification records individual documentation or
local package outcomes as satisfied.

## Cross-phase integration and end-to-end flows

The shared state path is wired from the public library API through the runner and
libretro callbacks. The runner and libretro tests exercise the same canonical
state contract; exact-source native and PowerPC/QEMU evidence passed locally.
No source-level cross-phase API break was found.

The README install consumer and Playstead handoff documentation are present. They
establish local package and integration-contract readiness, not a complete player
session. The released-core RetroArch attempt passed DMA comparison but failed the
held-input acknowledgement and skipped remaining input/battery/aggregate checks;
no paired Playstead result exists. The Phase 14 host route is wired but its
recorded attempt stopped in preflight before RetroArch launched.

The local CI workflow and release checks passed on the current source. That does
not establish released-core host acceptance, published-byte replay, paired
Playstead behavior, Windows performance improvement, or actual RetroArch
save/load/rewind/run-ahead behavior.

## Deferred scope

Defer TUNE-06, TUNE-07, PLAY-01–04, and FRONT-02–04 from v3.0 acceptance. Preserve
their requirement IDs, evidence, failures, and attempt limits in the archived
requirements and phase records. Reconsider them when selecting a later milestone;
the next milestone is scoped separately around the existing WebAssembly
portability direction and begins with the required pipeline tune-up.
