# Optional emulator interface: initial read

**Checked:** 2026-10-30. Muhtari facts below refer to repository HEAD `26c8268f9c56db39308287eaceb935e97eaf3a77`. External material is official API/documentation or a public issue report; no GPL/LGPL/unlicensed emulator implementation source was opened. This is high-level research, not an API specification.

## What exists today

The muhtari C API already provides a per-handle interface: create/destroy an opaque `muhtari *`, load copied media with region/BIOS/device/expansion choices, set structured input, run one frame with optional video/audio buffers, query AV info, inspect cartridge metadata, get RAM spans, and read frame/lag counters. It also reports API/ABI/behaviour revisions and lets callers supply an allocator ([`include/muhtari.h`](../../../include/muhtari.h)). The header does not promise thread safety or concurrent independent-instance behavior. It has no state serialize/restore API, register snapshot, instruction/bus hook, read-only CPU-bus peek, or batch-frame function. Its RAM and battery data pointers are mutable, so this is not yet a read-only observer surface.

Libretro already handles the ordinary frontend boundary: audio/video/input callbacks, system metadata and AV timing, environment callbacks, menu-style core options, memory descriptors, memory-region access, and optional serialize/unserialize. `retro_run()` advances one video frame at a time; a host can loop it. Its functions have no instance handle, and the official guide explicitly describes the core contract as single-instance, allowing global state. The local [`libretro.h`](../../../libretro/libretro.h) header itself carries an MIT notice, limited to that header. The official registry lists the API as MIT and RetroArch as GPLv3: a permissive header does not relicense a frontend runtime or another core. ([Libretro core guide](https://docs.libretro.com/development/cores/developing-cores/), [license registry](https://docs.libretro.com/development/licenses/))

The actual gaps are smaller than “another emulator API”:

| Need | Interface gap | Core/host/application boundary |
|---|---|---|
| **Inspection/debugging** | Muhtari exposes RAM spans and frame/lag counters, but no read-only, semantically named machine snapshot, registers, side-effect-free bus peek, break/step, or event hooks in its current public header. Libretro memory access is useful for conventional frontends, but is not a cross-core register/trace API. | Core must implement any truthful machine-specific observation/hook. A frontend, debugger, or script decides how to display, log, and control it. Hooks need a disabled-path cost contract and side-effect rules. |
| **Automated play / AI** | Muhtari accepts frame input and runs one frame; a host can loop. No standard endpoint today returns a typed observation/action result or a bounded batch. | Core supplies pixels and machine state. Host supplies the Gymnasium adapter, batching/vectorization, and episode lifecycle. Game-specific reward, “done,” level, score, and goal semantics require title knowledge. |
| **Configuration** | Muhtari’s C `media` input and libretro core options cover current load/runtime choices. Libretro options are a standard menu/config surface; a new interface could expose a programmatic profile, but must not just mirror every option in another schema. | Core owns valid effective settings and reports what was selected; frontends own config UI/default persistence. Game-specific input/action profiles belong with the game integration. |
| **State and saves** | Libretro already has optional serialize/restore; Muhtari’s current C header exposes battery bytes/generation but not save states. | Core defines state compatibility and validates restore. Host owns file/cloud custody, rotation and UX. Battery media and save states are different artifacts. Do not promise cross-core or cross-version interchange. |
| **Performance** | No source evidence shows the libretro boundary is a bottleneck. Both APIs advance one frame per call. | Core workload and rendering dominate until a same-work benchmark proves otherwise. A batch function may reduce FFI crossings for Python/WASM callers, but that is a hypothesis to measure with equal emulated work and identical observations. |

The distinction matters: a portable interface can make the mechanism for stepping/observing/configuring more uniform; it cannot infer what a particular game’s bytes mean or whether a score change is good. Gymnasium’s `step()` returns observation, reward, termination/truncation, and `info`; those are environment semantics, not properties an emulator core can infer in general. Stable-Retro documents per-game integration files for initial state, RAM variables, reward, and done conditions, which is strong evidence that useful automation needs a game profile alongside an emulator API. ([Gymnasium API](https://gymnasium.farama.org/v1.3.0/api/env/), [Stable-Retro integration docs](https://stable-retro.farama.org/v0.9.1/integration/))

## Patterns and limits

MAME’s Lua layer demonstrates a rich host scripting surface: device/state introspection, CPU registers, memory access, frame events, instruction stepping, breakpoints, and watchpoints. MAME itself warns that its Lua API is not stable. BizHawk’s Lua function reference documents memory, callbacks, movies and debug controls; these are concrete host-specific tools, not a shared emulator standard. ([MAME Lua overview](https://docs.mamedev.org/luascript/index.html), [MAME debugger API](https://docs.mamedev.org/luascript/ref-debugger.html), [BizHawk Lua function reference](https://tasvideos.org/Bizhawk/LuaFunctions))

One BizHawk user issue reports that a Lua memory search over a large memory domain took about nine seconds and asks for a built-in optimized search. Treat this only as a single anecdote: it suggests script-level convenience does not guarantee fast inspection, but says nothing about prevalence or about Muhtari’s performance. ([issue #4760](https://github.com/TASEmulators/BizHawk/issues/4760))

RetroArch’s “AI Service” is a narrow screenshot-service endpoint rather than a general emulator control/inspection API: its documented primary loop captures the rendered screen and sends it to a configured service for OCR/translation/accessibility output. It can include frontend input state and accept requested button presses, but it does not provide machine memory/register observations or deterministic training semantics; automatic polling also has CPU-load considerations. ([AI Service guide](https://docs.libretro.com/guides/ai-service/))

## Alternatives

| Path | Benefit | Cost / limit | Assessment |
|---|---|---|---|
| **Do nothing beyond libretro plus current C API/runner tooling** | Preserves the standard frontend route; the C API already serves direct deterministic callers, and the runner has headless frames, movie input, hashes, diagnostics and benchmarking. Future hooks/inspection can follow the existing YAGNI order in [HOSTS §5](../../preparation/HOSTS-AND-INTEGRATION.md#5-scripting-and-automation-yagni-order). | Separate consumers may each create bespoke adapters; current public C API lacks safe read-only inspection and savestates. | Best default until a concrete consumer demonstrates a missing operation that cannot be handled with the existing API plus a thin wrapper. |
| **Optional capability/profile and consumer adapters alongside libretro** | Adds a narrow, machine-readable way to query capabilities/effective settings and use instance-owned headless operations while retaining libretro for normal frontends. An adapter can expose Gymnasium without putting reward rules in the core. | Still Muhtari-specific until another core and independent hosts adopt it; duplicates concepts if it mirrors every C field or libretro option. New hooks can add hot-loop cost, unsafe mutation, and compatibility burden. | Most promising experiment if Playstead or a Python/browser automation caller has a repeated need. Prefer extending/adapting the existing C API first; do not assume an Emscripten, JSON, socket, RPC, Python, or AI framework choice before the target consumer is scoped. |
| **New cross-emulator standard** | Could give tool authors one contract across unrelated cores and hosts. | Needs multiple cores, host implementations, conformance fixtures, capability negotiation, versioning and security/ownership rules before it produces ecosystem value. Risks standardizing Muhtari-specific assumptions. GPU/accelerated or complex systems would expand scope. | Not justified by current evidence; preserve libretro. |

## Recommendation

Keep libretro as the supported game/frontend ABI and treat the C API as Muhtari’s direct instance-oriented automation seam. Do not start a second general standard now. If a real caller appears, run one small, approved vertical experiment using Muhtari plus either Playstead or the browser host: configure one known profile, step a deterministic input sequence without presentation work, compute frame/audio hashes over output buffers, and copy one raw RAM/counter observation. Add a typed read-only snapshot only if that proves necessary; state round-trip belongs after a state API exists. Repeat through a second adapter only if the first consumer establishes a durable need. Measure identical work before claiming speed gains. The experiment should test whether current C calls and a thin adapter suffice before adding a versioned capability/profile layer.

Keep the first proof to the current 7800 software path and deterministic fixtures. Do not include GPU acceleration, cloud/network RPC, a machine-learning runtime, or arbitrary multi-console policy. Add only the particular register/hooks/batch operation that the proof shows is missing; observers should be read-only by default, hooks opt-in, and state/saves explicit about compatibility and ownership. A new “standard” becomes worth revisiting only after a second independently implemented core and at least two independent host/tool consumers can run the same conformance cases.

This recommendation changes if a Playstead/browser consumer cannot express a real workflow through Muhtari’s current C API plus a thin wrapper, if equivalent-work measurements isolate meaningful boundary overhead, or if another emulator project is ready to implement and test the same narrow contract. A feature request for AI in the abstract is not enough: the missing observation/action, game profile, and acceptance result must be named first.
