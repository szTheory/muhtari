## Recommendation

Recommend a deliberately small **SEED-004 developer trace milestone**: add an opt-in, headless instruction and bus-access trace to `muhtari-run`, scoped to a selected frame and address range, with tick/beam location and CPU state in each record. Reuse the planned optional observer seam; defer interactive stepping, GUI, Python/Gymnasium, Lua, BK2, patching and linting. This helps developers diagnose banked code and timing issues without inventing a current player defect. The developer-authored [7800 debugger guide](https://7800.8bitdev.org/index.php/Introduction_to_the_MAME_debugger) calls breakpoints and watchpoints core tools; [Debugging on Ancient Game Platforms](https://7800.8bitdev.org/index.php/Debugging_On_Ancient_Game_Platforms) describes instruction traces, memory inspection and stepping as practical debugging methods. This supports ecosystem value, not direct proof of a current Muhtari customer request.

Acceptance is locally tractable: use owned MIT diagnostic/generated inputs, assert a small numeric trace and event-order oracle, and show that enabling tracing does not change frame/state hashes. The existing design already specifies an optional dual-compiled trace loop and an off-path cost check ([ARCHITECTURE §8](../../preparation/ARCHITECTURE.md#8-observability), [ENGINEERING §8](../../preparation/ENGINEERING.md#8-performance-engineering-and-the-ratchet)); the current [public header](../../../include/muhtari.h) is API 8 and has no observer API, and [runner options](../../../docs/runner.md#options) have no trace facility. The selected scope is runner-only and keeps public API 8 unchanged; pause for an explicit compatibility decision if a public observer API proves necessary. Keep callbacks and trace buffers host-owned and out of machine state. No emulator host, hardware, copyrighted ROM or external code is needed for acceptance.

## Diminishing-returns rule

Keep the next implementation to one trace slice and close it when its generated acceptance, deterministic no-change behavior and hooks-off cost gate pass. Do not expand into the rest of SEED-004 or add compatibility cases just to consume the untested title count. Before any later title expansion, define a finite rights-cleared set and an independent criterion for each named gameplay sequence; stop expanding when every item has a reproducible result and none exposes a source-qualified core blocker. Add cases only when a new report or independent evidence supplies them. Otherwise, move broad feature work to maintenance-driven fixes and keep hardware uncertainty documented without measurement-only phases.

**Confidence:** High for current repository constraints and testability, based on the pinned project snapshot; medium for external ecosystem value and accessory behavior, based on primary developer documentation. The title-search result is inconclusive; no negative claim about all available homebrew licenses is made.

Research only; no builds, tests, emulators, hosts or hardware checks were run.
