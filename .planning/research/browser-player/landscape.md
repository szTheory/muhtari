# Browser player and libretro host landscape

**Checked:** 2026-10-30. Read only official project README/docs and license metadata; no emulator implementation source, packages, cores, ROMs, or BIOS files were opened or downloaded. GitHub source pins below are the repository `HEAD` hashes observed during this review. Product claims are source-backed; fit and reuse conclusions are labeled as inferences. This is a landscape, not an implementation or legal opinion.

## Build boundary

The browser core must be built for the chosen WebAssembly toolchain and host contract. The RetroArch path builds for Emscripten and statically links the core into RetroArch; `libretro-wasm` builds WASI modules and supplies WASI imports in JavaScript. A native `.so` is a different machine-code and ABI artifact and cannot be loaded directly as a browser WebAssembly core. This is an inference from the two projects' documented build formats; the later web target should choose one toolchain/ABI and produce a dedicated artifact.

## Recommendation

If a web companion is worth pursuing, keep it as a separate, small MIT-licensed player that builds Muhtari specifically for a browser WASM target and uses browser facilities for display, audio, and input. Start with the Muhtari core plus only the thin host surface needed for local play; don't inherit RetroArch's runtime/assets or unrelated cores. Keep ROM, BIOS, and save/state bytes user-supplied and local, and pin every generated JS/WASM input at release time. This reuses the settled web direction in [HOSTS-AND-INTEGRATION §6](../../preparation/HOSTS-AND-INTEGRATION.md#6-wasm-seed-008-the-hash-lane-may-come-in-phase-1) and adds no dependency unless evidence shows the host code would be materially safer or smaller with one.

For Muhtari's current Playstead consumer, treat that as a companion candidate: the inspected Mac adapter launches a verified native child process, while the existing Phoenix web console has library/preview/save surfaces but no emulator/playhead. A web surface exists; browser play itself is not qualified. Current-source references and dirty-worktree limits are in [Playstead fit](playstead-fit.md). Keep muhtari's proposed external RetroArch integration as the immediate route; this research does not establish that Playstead already implements it.

This recommendation changes if (a) Playstead promotes a supported browser-play surface, (b) full RetroArch menus/shaders/save management become a requirement and the owner accepts a separately scoped distribution review, (c) `libretro-wasm` publishes a clear permissive host license and pinned dependency provenance, or (d) a concrete browser target cannot meet performance/input/save needs. Emscripten is the existing muhtari harness recommendation, not a settled multi-core host architecture. A first follow-up should be a narrow product seam check in Playstead, not a new muhtari deliverable or implementation plan.
